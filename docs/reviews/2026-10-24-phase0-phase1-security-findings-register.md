## Phase 1 — P-01 through P-05 Disposition

### P-01 — `dso.yaml` configuration file permissions

**Classification: Accepted risk with documented rationale, consistently enforced only via warning, not fail-closed. No code fix applied.**

- `pkg/config/permissions.go:23-38` (`PermissionAdvisory`): read-only check, explicitly documented as never chmod-ing the file itself ("the path may be user-supplied and chmod-ing it behind the operator's back could break their deployment"). Called from `internal/cli/config.go:94` and `internal/cli/agent.go:103` — i.e., surfaced to the operator at `config` and `agent` command time, not enforced.
- `internal/bootstrap/permissions.go`: install-time, `setupDSOFiles` sets `/etc/dso/dso.yaml` to `dsoConfigFileMode = 0640` (line 288, 306) and *tightens* an existing file toward that bound (`tightenMode`, line 294) during a fresh bootstrap. `VerifyPermissions` (lines 398-471) is advisory-only — it logs `Warn` for wrong owner/group/mode and **never returns an error or blocks startup** (`return nil` unconditionally at line 470).
- **Asymmetry confirmed**: key material in `internal/crypto`/`internal/securefs` is fail-closed (rejects insecure permissions on open, per the earlier security audit's F-06). `dso.yaml` — which holds the WebUI password hash and provider credentials — is never rejected, only warned about, at both config-load time and `dso doctor`/bootstrap-verify time.
- This matches SECURITY.md/THREAT_MODEL.md's documented stance ("protect like /etc/passwd," operator responsibility) and the code comment explicitly justifying why it's advisory rather than enforced (compatibility/deployment-safety tradeoff). **Classified as accepted risk with documented rationale, not a confirmed defect** — but flagged as a real inconsistency worth a product decision: either (a) explicitly accept the asymmetry as documented, or (b) add an opt-in fail-closed mode for operators who want parity with the key-file guarantee. No code change made this pass — doing so without a product decision would risk breaking existing deployments, which the existing code comment explicitly warns against.
- **Decision record written**: `docs/reviews/2026-10-24-p01-config-permissions-decision.md`. Summary: keep the existing `dso.yaml` advisory-only behavior as an accepted, documented risk for compatibility reasons; **new `dso central` credential files should default to fail-closed permission enforcement** (mirroring `securefs`'s key-file convention) since they are new code with no existing-deployment compatibility constraint. No change was made to `dso.yaml`'s existing enforcement.

### P-01 addendum: `rejectEscapingSymlink` defect (confirmed and fixed)

While re-running the `TestIsSafePath_*` tests from the Phase 0 baseline (not merely re-reading file existence), a real logic defect was found and fixed in the code this P-01 item is directly about:

- **Defect**: `pkg/config/config.go`'s `rejectEscapingSymlink(baseAbs, fullAbs)` resolved the candidate path's parent directory through `filepath.EvalSymlinks` (to catch an intermediate symlink escaping the base directory) but then compared that *resolved* path against the **unresolved** `baseAbs`. Whenever `baseDir` itself sits under a symlinked ancestor unrelated to the user-supplied path — macOS's `/var` → `/private/var` (which is exactly what `t.TempDir()` sits under, and what a real-world `/tmp`-based deployment could also hit) — `filepath.Rel` compared two paths in different "coordinate systems" and falsely reported `path traversal detected: resolved path escapes base directory via a symlinked parent directory` for a perfectly legitimate path.
- **Impact**: availability/correctness, not confidentiality — the bug fails *closed* (rejects a legitimate operation) rather than open, so it was never a security hole. But it directly affects confidence in this exact symlink-defense code that P-01 and the broader audit were examining, and it would reject legitimate `dso` operations (e.g. `export`, or any `IsSafePath`-gated write) on any real deployment where the configured base directory happens to live under a symlinked parent.
- **Evidence it is a real defect, not a macOS test artifact**: traced the exact comparison in `rejectEscapingSymlink` (previously at pkg/config/config.go:1010-1018) and confirmed `baseAbs` was never passed through `EvalSymlinks` while the parent it was compared against always was. This asymmetry exists independent of the OS; macOS's `/var` symlink simply made it trivially reproducible via `t.TempDir()`.
- **Fix applied** (pkg/config/config.go, `rejectEscapingSymlink`): resolve `baseAbs` through `filepath.EvalSymlinks` the same way the parent is resolved (falling back to the unresolved `baseAbs` if `EvalSymlinks` fails, e.g. the directory doesn't exist), then compare both resolved paths. This is symmetric and does not weaken the real escape check: by manual trace, the existing `TestIsSafePathSymlinkEscapeAttempt` test (an intermediate symlink pointing at a genuinely different, sibling directory under the same temp root) still correctly fails after the fix, because resolving both sides the same way still diverges at the point the symlink points somewhere else — only the previously-false "the base directory's own unrelated ancestor happens to be a symlink" case is now correctly allowed.
- **Regression verification**: `go build ./pkg/config/...` and `go vet ./pkg/config/...` clean; `go test ./pkg/config/... -run TestIsSafePath -v` — all 8 `TestIsSafePath*` subtests pass, including the pre-existing escape-detection and leaf-is-symlink regression tests (`TestIsSafePathSymlinkEscapeAttempt`, `TestIsSafePath_LeafIsSymlink`). No new test was added — the existing `TestIsSafePath_NewFileNotYetExisting` and `TestIsSafePath_SymlinkedParentDirNotEscaping` already serve as the regression tests for this exact defect and now pass.
- **File changed**: `pkg/config/config.go` (uncommitted, per instructions — see Step 1 verification above for the full working-tree state).

### P-04 — "Docker-socket proxy authorization"

**Classification: Scope correction — the component the prior audit speculated about does not exist in the form assumed; no authorization boundary was found to be missing because there is no such boundary by design.**

- `internal/proxy` was read directly this pass (not done in the prior audit, which only inferred from the package name and test filenames). It is **not** a Docker-socket access-control/mediation layer. It is DSO's own TCP reverse-proxy for **zero-downtime connection draining during rotation** — `Manager`, `Registry`, `Router`, and `Backend` types that own host-port→container-port mappings and swap traffic between the old and new container during a rotation (`internal/proxy/manager.go:1-40`, `DrainWindow` constant, `SwapBackend`). `manager_ownership_test.go` concerns which DSO-managed proxy "owns" a given host port, not container access scoping.
- **There is no separate Docker-socket mediation/authorization component in this codebase.** The DSO agent process holds a direct `docker/docker/client.Client` connection to the Docker socket (used throughout `internal/rotation`, `internal/injector`, `internal/watcher`). Access to that socket is governed entirely by OS-level `docker` group membership — the same trust boundary any Docker CLI user has, already documented in THREAT_MODEL.md's Docker-daemon trust-boundary section and the prior security audit's "verified clean" notes (full daemon environment, root-compromise-is-full-compromise assumption).
- **Conclusion: this P-04 item, as originally scoped ("which Docker API methods are permitted," "can callers access arbitrary containers or projects," TOCTOU on ownership changes"), does not map to a real component to review** — DSO does not claim or implement per-caller Docker API scoping, and none should be assumed to exist. This is reported back as a scope correction rather than either "verified safe" or "confirmed defect," since there is nothing to verify or fix at that boundary; the actual, already-documented trust boundary is "whoever can reach the agent process/socket has full Docker access," which is accepted and disclosed, not hidden.

### P-05 — CI workflow permissions

**Classification: One confirmed, now-fixed defect; the rest verified safe. The fix itself has now been structurally validated (not live-tested against an actual fork PR).**

**Validation performed this pass:**
- **YAML syntax**: `.github/workflows/coverage.yml` parses successfully (`ruby -ryaml -e "YAML.load_file(...)"` — no `python3`/`yaml` module or `actionlint` binary was available in this sandbox, so Ruby's YAML parser was used as the available structural check; this confirms valid YAML syntax, not GitHub Actions semantic correctness).
- **Expression semantics, verified by manual trace against documented GitHub Actions behavior** (no live execution): `if: github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository`
  - On `push` to `main`: `github.event_name` is `'push'`, so the left side of `||` is `true` → step runs. The right side (`github.event.pull_request.head.repo.full_name`) safely evaluates to `null` on a push event (GitHub Actions expression property access on an absent object returns `null` rather than erroring), so there is no missing-metadata crash — confirmed this is standard, documented GitHub Actions expression behavior, not run live.
  - On a same-repository PR: left side `false`; right side `head.repo.full_name == github.repository` is `true` → step runs.
  - On a fork PR: left side `false`; right side is `false` (fork's `full_name` differs from `github.repository`) → step is **skipped**.
  - Skipping a step does not fail the job (GitHub Actions treats a skipped step as neutral, not a failure), and `fail_ci_if_error: false` was already set on the Codecov action itself as a second-layer safeguard. **No live fork-PR workflow run was performed in this pass** — this is a structural/semantic trace, not an executed test, and is reported as such per the instruction not to claim a live test that wasn't performed.
- **Re-confirmed the rest of P-05's prior findings unchanged**: no `pull_request_target` or `workflow_run` anywhere in `ci.yml`/`release.yml`/`coverage.yml`; `release.yml`'s elevated permissions remain scoped to `push: tags: [v*]` only.

- **Confirmed and fixed**: `.github/workflows/coverage.yml` referenced `secrets.CODECOV_TOKEN` inside a step that runs on the plain `pull_request` trigger (lines 6-7, 56-59). Unlike `pull_request_target`, plain `pull_request` does give the fork PR's workflow run a **read-only** `GITHUB_TOKEN` (already correctly scoped: `contents: read`, `checks: write`, `pull-requests: write` at lines 9-11) — but other repository secrets, including `CODECOV_TOKEN`, are still injected into that job regardless of fork origin. A malicious fork PR could add a step that prints or exfiltrates `$CODECOV_TOKEN`. **Fix applied**: added `if: github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository` to the "Upload to Codecov" step, so it still runs on pushes to `main` and same-repo PRs, but is skipped for fork PRs (uncommitted; see below). `fail_ci_if_error: false` was already set, so the skip doesn't fail the job. No regression test is applicable to a CI workflow guard; verification is structural (the condition is standard, documented GitHub Actions syntax) — **not executed in a live fork-PR scenario in this pass**, since that would require an actual fork PR against this repository.
- **Verified safe**: neither `ci.yml`, `release.yml`, nor `coverage.yml` uses `pull_request_target` or `workflow_run` anywhere — the specific dangerous combination the task asked about (untrusted PR code + elevated permissions/checkout-of-base-workflow) is absent. `ci.yml` is `contents: read` only. `release.yml`'s elevated permissions (`contents: write`, `id-token: write`, `packages: write`) are scoped to a `push: tags: [v*]` trigger only — tags are pushed by maintainers, not arbitrary contributors, so this is an appropriate, not excessive, grant for GoReleaser + cosign + container publishing. No other secret references beyond `CODECOV_TOKEN` and the standard `GITHUB_TOKEN` were found in any of the three workflows.
- Action version pinning: `actions/checkout@v4`, `actions/setup-go@v5`, `codecov/codecov-action@v4`, `actions/github-script@v7` — pinned to major version tags, not full SHAs. This is a lower-severity supply-chain hardening opportunity (major-version tags can be moved by the action's maintainer) but was not treated as a defect requiring an immediate fix in this pass, since it's a broader, repo-wide convention decision rather than a specific excess-permission bug — flagged for a future product/engineering decision rather than fixed unilaterally here.

## What remains before Phase 2 can start

Per the plan, Phase 2 (`dso central` authentication/authorization/audit-chain/backup work) should not begin until this register is reviewed. With P-03 now closed and P-01 now documented as a decision, the remaining open items are narrower:
- **P-01's recommendation** (fail-closed-by-default for new central-store credential files) should be explicitly accepted or overridden by a product decision before `dso central`'s own credential storage is designed, since that design directly depends on it.
- **The Docker-socket-unreachable sandbox limitation** means none of the Docker-dependent test packages (`internal/agent`, `internal/events`, `internal/cli`, `test/integration`, `pkg/backend*`, and the Docker-socket-dependent `pkg/config` tests) were actually exercised pass/fail in this environment, in either pass. This is an infrastructure gap in *this review environment*, not a known code defect — but it means Phase 2 work that touches any of those paths will need verification in an environment with a reachable Docker daemon before it can be considered tested, not just built.
- **The macOS unix-socket-path-length test failures** in `internal/agent` remain unverified on Linux (no cross-platform reproduction was available in this sandbox); no fix was attempted since there was nothing to validate it against.
- **The `TestLoadConfigWithOwnerID_PersistsOnceAndIsStable` panic** (an `err`-check-ordering nit in the test itself, not production code) is noted but intentionally left unfixed, since it is masked by the Docker-socket infrastructure gap rather than a defect in the code under test.
